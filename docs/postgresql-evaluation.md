# PostgreSQL 迁移评估

> 适用版本：v2.6.2
> 结论：v2.6.2 已支持可选 PostgreSQL 运行时；未设置 `DATABASE_URL` 时继续使用 SQLite。

## 当前架构

- SQLite + `better-sqlite3`，WAL 模式。
- 任务队列、任务、日志、ASR、自动化、通知、Token、质量校验全部在同一数据库。
- 单容器默认；多 Worker 通过 SQLite 原子 `UPDATE ... WHERE status='queued'` 抢占任务。
- 运行中心跳每 10 秒更新，启动时只回收超过 `SUBX_WORKER_STALE_SECONDS` 的陈旧任务。

## 适合 PostgreSQL 的场景

- 多台主机共享任务队列。
- 多 Worker 高频抢任务。
- 任务/日志/审计数据量达到数百万行。
- 需要在线备份、只读副本、细粒度权限。
- 需要避免网络文件系统上的 SQLite 锁问题。

## 不适合立即迁移的场景

- 单 NAS、单容器、几十到几百个任务/天：SQLite 足够。
- 媒体目录与数据库都在同一台 NAS：SQLite 运维更简单。
- 目前所有 SQL 使用同步 `better-sqlite3` API，迁移需要异步驱动和较大范围改造。

## 迁移工作项

1. 抽象数据库访问层，替换 `better-sqlite3` 同步调用。
2. 使用 `pg` / Drizzle / Kysely 之一，统一参数占位符和事务。
3. 改写 SQLite 专有语法：
   - `datetime('now')` → `now()`
   - `INSERT OR REPLACE` / `INSERT OR IGNORE` → `ON CONFLICT`
   - `AUTOINCREMENT` → `GENERATED BY DEFAULT AS IDENTITY`
   - `PRAGMA` / WAL 配置移除
4. 迁移 JSON 文本字段，可选升级为 `jsonb`。
5. 任务队列抢占改为 `SELECT ... FOR UPDATE SKIP LOCKED`。
6. 迁移测试：schema、索引、唯一约束、事务、回滚、备份恢复。
7. 提供 SQLite → PostgreSQL 一次性迁移脚本。
8. 保留 SQLite 作为默认嵌入式模式，PostgreSQL 作为可选 `DATABASE_URL` 模式。

## 已提供的迁移工具

```bash
DATABASE_URL=postgres://user:pass@host:5432/subx \
  node scripts/export-sqlite-to-postgres.mjs --sqlite ./data/db/subx.db
```

- 先执行 `scripts/postgres-schema.sql` 建表。
- 按表复制数据，唯一冲突跳过。
- 自动重置 identity 序列。
- 该工具只迁移数据，不改变主应用当前使用 SQLite 的事实。
- 完整运行时切换仍需完成异步 DB 访问层。

## 运行时切换

```env
DATABASE_URL=postgres://subx:password@127.0.0.1:5432/subx
PG_POOL_SIZE=5
```

- 设置 `DATABASE_URL` 后自动创建 schema。
- 未设置时继续使用 SQLite。
- 任务队列通过原子更新抢占，支持单主机/多主机多 Worker。
- 启动时只回收 heartbeat 超过 `SUBX_WORKER_STALE_SECONDS` 的陈旧任务。
- 同步 SQLite 风格 API 由 worker + 共享内存桥接，适合 NAS 低并发场景；查询会阻塞 Node 事件循环，不建议高并发部署。
- 高并发场景建议改用异步 DB 层并独立部署 PostgreSQL；当前 `PG_POOL_SIZE` 受串行桥接限制。

## 建议

- 单机低并发继续 SQLite。
- 多主机、多 Worker、大任务量使用 PostgreSQL。
- 若出现多主机 Worker 或任务队列锁竞争，再启动 PostgreSQL 适配。
- 多 Worker 在单主机共享本地卷上可继续 SQLite，但不要把数据库放在 NFS/SMB 上。
